# M15c Web Build Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The app compiled to WebAssembly and served as a static site: WebGPU with a WebGL2 fallback (light shadows off on WebGL2, and the app says so), files opened through browser uploads (or the File System Access API) and saved as downloads (or written back through the File System Access API), the in-app menu bar, prefs in browser storage; no agent socket in the browser (the MCP server stays native).

**Architecture:** Three steps. (1) The shared crates (kernel, session, tools, render, api without its transport) build for `wasm32-unknown-unknown`: wall-clock and monotonic time go through `web-time` (same API, works on both), blocking GPU validation is replaced by capability checks, the renderer requests WebGL2 downlevel limits on the GL backend, and the session gains byte-based open/import/save entry points next to the path-based ones. (2) The `app` crate becomes a library plus a thin native binary; native-only modules (CLI, headless, MCP, agent socket, native menus and dialogs, recovery files, library folder, print spawning, arboard clipboard, env_logger) are behind `cfg(not(target_arch = "wasm32"))`, and the window code takes its platform services (file open/save, prefs storage, message boxes, clipboard) through a small trait implemented natively and for the web. (3) A new `web` crate (cdylib) starts the same app on a `<canvas>` with winit's web event loop, creates the GPU device asynchronously (WebGPU first, WebGL2 fallback), and implements the web platform services with `web-sys`. `scripts/build-web.sh` builds the release wasm, runs `wasm-bindgen --target web`, and writes `web/dist/` (index.html, JS glue, wasm). CI checks the wasm build.

**Tech Stack:** Rust 2024 (wasm32-unknown-unknown), wgpu 30 (webgpu + webgl), winit 0.30 web, egui 0.36.2; new direct dependencies approved by the user and already in `Cargo.lock`: `wasm-bindgen =0.2.129`, `web-sys =0.3.106`, `js-sys =0.3.106`, `wasm-bindgen-futures =0.4.79`, `web-time =1.1.0`, `getrandom` (the `wasm_js` feature for wasm only). Tools on the machine: the `wasm32-unknown-unknown` target and `wasm-bindgen-cli 0.2.129` (installed with the user's approval). No hosting: the site is served locally for testing.

**Spec:** `docs/superpowers/roadmap.md` row M15c; user decisions 2026-10-22 (all setup approved, no hosting yet).

## Global Constraints

- Only the dependencies listed above may be added, at the exact versions already in `Cargo.lock`; `Cargo.lock` gains no new package (check `git diff Cargo.lock`: only dependency lines of our crates may change, plus any feature-only changes).
- Native behaviour, golden images, `.skr` format and the agent API are unchanged; the native gate stays green.
- The gate adds a wasm check from Task 1 on: `cargo check --target wasm32-unknown-unknown -p kernel -p session -p tools -p render` (Task 1), plus `-p web` (Task 3). `getrandom` needs `--cfg getrandom_backend="wasm_js"` for wasm: put it in `.cargo/config.toml` under `[target.wasm32-unknown-unknown] rustflags`.
- No `Instant::now()` / `SystemTime::now()` from `std` in code that runs on the web (they panic there): use `web_time::{Instant, SystemTime}` in shared code.
- Gate per task (project rules in the SDD rules files): `cargo fmt --all --check && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace --lib --bins --tests` plus the wasm check above; Windows clippy runs in CI.
- Docs: a new `docs/web.md` (build, serve, what works and what is off on the web). No emoji. Short commit messages. Never `git add -A`.

## Spec notes (rulings)

1. **Shared crates on wasm:** kernel, session, tools, render compile for wasm32 with no `cfg` noise beyond what is needed; `api` builds for wasm with its transport module and socket re-exports behind `cfg(not(target_arch = "wasm32"))` (the web app does not run a hub). `render::Snapshotter` (blocking readback) is native-only.
2. **Renderer on the web:** backends `BROWSER_WEBGPU | GL`; WebGPU preferred. On the GL backend the device is requested with `Limits::downlevel_webgl2_defaults()` raised to what the adapter allows for the texture array layers we need; light shadows are off when the adapter lacks cube-array textures (`DownlevelFlags::CUBE_ARRAY_TEXTURES`) — decided by capability, never by `block_on`; the window shows "Light shadows are off in this browser (WebGL2)" once in the status line and in Help > About. MSAA 4x when the format supports it, otherwise 1x.
3. **Session bytes API:** `Document::open_bytes(name, bytes, discard)` (`.skr`, and `.skp` as open-as-document), `Document::import_bytes(name, bytes, options)` (OBJ, STL, SKP), `Document::save_bytes() -> Vec<u8>` (marks the document clean like Save; the name is the document's name or "untitled.skr"), `Document::export_bytes(format) -> (Vec<u8>, report)` for OBJ/STL/glTF/SKP/SVG — each sharing the existing code paths (no duplicate readers/writers).
4. **App as a library:** `crates/app/src/lib.rs` exposes the window app (`App`, its run entry taking a `Platform` implementation and an optional pre-created GPU context); `main.rs` keeps the CLI and native modes. Native-only modules compile only natively. A `Platform` trait covers: open a file (async-capable: returns name + bytes via a callback/event), save bytes under a suggested name, read/write prefs text, show a message box with buttons (the unsaved-changes prompt), clipboard text get/set, open a URL. Native implements it with rfd/fs/arboard as today; behaviour unchanged.
5. **Web app:** `crates/web` (`cdylib`, `#[wasm_bindgen(start)]`): finds or creates `<canvas id="sketchup-alt">` filling the window, runs winit's web event loop (`spawn_app`), requests the GPU adapter/device asynchronously before creating the app state, hands keyboard/pointer/resize through winit, uses the in-app egui menu bar (no native menus). Files: File > Open shows `<input type=file accept=".skr,.skp">` (or `showOpenFilePicker` when available, keeping the handle so Save writes back to the same file); File > Save downloads `<name>.skr` (or writes to the kept handle); Save As always asks (picker when available, else download); Import/Export like Open/Save with their formats. Unsaved-changes prompt is an in-app egui dialog. Prefs in `localStorage` key `sketchup-alt-prefs` (same JSON as prefs.json). Off on the web and hidden from menus: Library, autosave/recovery, Print/Export PDF, Open Recent, agent socket/MCP. Clipboard: egui's built-in clipboard events (copy/paste of clips between browser tabs through text).
6. **Build and serve:** `scripts/build-web.sh` (release build of `web` for wasm32, `wasm-bindgen --target web --no-typescript --out-dir web/dist`, copies `web/index.html`); `scripts/serve-web.sh` serves `web/dist` on `http://localhost:8080` with the right MIME types (a tiny Python `http.server` with `.wasm` -> `application/wasm` is fine — Python is on the machine; document it). `web/dist` is git-ignored.
7. **CI:** the Linux x86_64 job adds the wasm32 target and runs `cargo check --target wasm32-unknown-unknown -p web` (with the getrandom cfg from `.cargo/config.toml`).

## Review Focus

1. The native app behaves exactly as before (all existing tests, golden images), including dialogs, prefs, recovery, library and print paths after the `Platform` refactor.
2. On the web, a model opened from an uploaded `.skr` edits, saves as a download that reopens identically, and a `.skp` upload opens as a model.
3. WebGL2 fallback: in a browser without WebGPU the app runs with shadows off and says so; nothing calls `block_on` or `std::time::Instant` on the web.
4. No panics on the web from time, threads, filesystem or process calls in reachable code (search the wasm build's reachable modules for `std::time::Instant`, `std::fs`, `std::thread`, `std::process`).
5. Keyboard shortcuts in the browser use Ctrl (and Cmd on macOS browsers) without fighting browser shortcuts where avoidable (prevent default for handled chords on the canvas).
